How Custos works

A cryptographic guardrail that makes it structurally impossible for a prompt-injected AI agent to authorize a payment it shouldn't — plus exactly what's real vs. simulated in this build.

The problem

An AI shopping agent holds a pre-authorized payment mandate — a fund block it can debit from without re-prompting for a PIN each time. If an attacker hides instructions inside content the agent reads (a product page, a support ticket, an email), the agent can be talked into authorizing a payment the user never asked for. System-prompt instructions and RAG-based policy hints are advisory text a model can be argued out of — they are not a security boundary.

Custos replaces "please don't" with "physically cannot": the LLM never has the authority to move money. It can only propose a payment. A separate, isolated policy engine — inside a real AWS Nitro Enclave in the production path — independently checks the proposal against the mandate and the user's actual words, and only that engine's cryptographic signature can make a payment gateway execute anything.

Architecture — three planes

The system is split into three trust domains that never share code or memory:

agent_orchestrator/

Agentic Plane

Untrusted. Runs the LLM conversation (FastAPI + a hosted tool-calling LLM). Generates a proposed tool call. Never talks to the payment gateway directly — every proposal is routed through the guardrail first.

enclave_service/

Enclave Plane

The guardrail. Checks the proposal's amount/recipient against the mandate and against what the user actually said. Only signs a JWT if it's genuinely approved — nothing here ever executes a payment itself.

ledger_gateway/

Ledger Plane

Deterministic executor. A Go service that verifies the guardrail's signature and nothing else. No signature, no execution — every request without a valid one is rejected before it touches the database.

End-to-end request flow

1
User sends a message

The orchestrator holds the conversation and may generate a tool call proposing a payment — amount, recipient, mandate ID.

2
Proposal routed to the guardrail, never the gateway

The orchestrator's only path to a payment is through the enclave's /guardrail/evaluate. There is exactly one call site to the gateway in the whole orchestrator, and it only fires after a signed approval comes back.

3
Guardrail checks the proposal against ground truth

Does the amount fit the remaining mandate balance? Does the amount or recipient actually appear in what the user said — or only in content the agent merely read? A proposal that only exists because of injected content gets rejected as a semantic mismatch, even if the LLM itself was fooled into generating it.

4
Approved → signed JWT, 5-second TTL

Signed with an RSA key that — in the real AWS path — only ever exists in plaintext inside the attested enclave's memory, decrypted on demand via KMS.

5
Gateway verifies the signature, not the story

The Go gateway never sees the prompt, the conversation, or the agent's reasoning — only a signature it checks against the public key. Expired, replayed, or unsigned requests are rejected before the database is ever touched.

6
Row-locked debit, append-only audit entry

SELECT ... FOR UPDATE on the mandate row prevents a race between concurrent proposals from ever double-spending the same budget.

The real AWS integration Verified

This isn't a diagram of what an enclave would do — the signing pipeline below was built and verified against actual AWS Nitro Enclave hardware:

  1. EC2 host — a Nitro-capable instance (Graviton c6g.xlarge, not the far pricier .metal family some older docs imply is required) with the enclave option enabled at launch.
  2. AWS KMS — a symmetric key seals the enclave's RSA signing key at rest. The key policy grants the host's IAM role exactly kms:Encrypt / kms:Decrypt / kms:DescribeKey on that one key — nothing broader.
  3. Attestation-gated decrypt — the enclave calls kmstool_enclave_cli (AWS's own NSM-attestation + KMS SDK tooling, built from source, not hand-rolled crypto) to decrypt the sealed key. This only succeeds if the enclave's measured PCR0 matches the KMS key policy's condition — a code integrity check enforced by AWS's hardware, not by anything this app trusts about itself.
  4. In-memory signing — the decrypted private key never touches disk. It signs approved JWTs locally inside the enclave and is discarded on process exit.
  5. VSOCK-only boundary — the enclave has no network interface at all. A small bridge process on the parent host relays requests over VSOCK and exposes the exact same HTTP contract as the local dev stub, so the orchestrator's code is identical whether it's talking to the local stub or the real enclave.

Full verification trail — including the real PCR measurements, the exact `kmstool` build recipe, and a false-positive bug that testing against the real enclave surfaced and how it was fixed — is in specs/001-payment-guardrail-mvp/tasks.md (search for "T-16" through "T-18").

What's real vs. simulated in this build

Real

  • LLM tool-calling agent, live API calls
  • Deterministic policy engine (mandate + semantic checks)
  • RS256 JWT signing and verification
  • Reject-by-default payment gateway with replay protection
  • Row-locked Postgres ledger, append-only audit log
  • AWS Nitro Enclave, attestation-gated KMS decrypt, in-memory signing

Simulated / out of scope

  • No live banking or UPI network integration — a mock gateway only, permanently by design
  • No custom-trained models — hosted LLM APIs only
  • Enclave's mandate ledger is seeded once at boot, not live-synced to Postgres (documented limitation, not hidden)
  • No merchant onboarding, multi-tenant auth, or account management

Measured results

From the adversarial evaluation suite, run end to end against the live system (not claimed — reproducible via adversarial_eval/run_eval.py):

100%
Injection payloads prevented
0%
False positives on legitimate requests
<1ms
Guardrail signing latency (post-boot)

One run included a payload that genuinely fooled the LLM — it generated a tool call for an amount and recipient the user never stated — and was still caught by the guardrail's semantic-mismatch check before the gateway was ever contacted. That's the actual claim this project makes: it doesn't matter if the model gets fooled, because the model was never the thing with authority to spend.

Deployment

The interactive demo on this site talks to real hosted services — this build isn't a mockup pointed at nothing:

  • Frontend — Vercel (static)
  • Orchestrator, gateway, enclave stub — Render (free tier — the first request after idle can take 30–60s while an instance wakes up)
  • Ledger database — Neon Postgres

This hosted path uses the local simulated enclave stub (deterministic policy engine, RS256 signing), not the real AWS Nitro Enclave — that one requires actual Nitro-capable EC2 hardware and isn't something a serverless platform can run. See the AWS integration section above for what was verified there instead.

To run the whole stack locally instead:

git clone https://github.com/Keerthivasan-Venkitajalam/custos.git
cd custos
docker compose up -d                     # Postgres
cd ledger_gateway && go run gateway.go & cd ..
cd enclave_service && uvicorn policy_engine:app --port 8100 & cd ..
cd agent_orchestrator && uvicorn main:app --port 8000 & cd ..
cd frontend && python3 -m http.server 8080

Full instructions, including the real AWS Nitro Enclave path, are in the repo's README.md and specs/001-payment-guardrail-mvp/.
